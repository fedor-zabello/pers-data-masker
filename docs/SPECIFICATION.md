# Спецификация — Модуль безопасности персональных данных

Сервис-прокси между системой-потребителем и LLM: идентифицирует персональные
данные (ПД) в тексте, маскирует их перед отправкой в LLM и демаскирует ответ.
Реализует единый контракт `POST /process` для нагрузочного тестирования.

Документ фиксирует архитектурные решения, принятые в ходе проектирования, и
служит основой для реализации. План работ — см. [PLAN.md](./PLAN.md).

---

## 1. Цели и ограничения

| Параметр | Значение |
|----------|----------|
| Качество идентификации/маскирования/демаскирования | ≥ 95% |
| Latency | ≤ 1 с (ориентир) |
| RPS | 1000 (цель), до 2000 (доп. плюс) |
| Объём текста | до 100 000 токенов |
| Таймаут одного запроса | 10 с (проверяющая система) |
| Идемпотентность | по `payload_id` (до 3 попыток) |

Ключевой принцип: обработка полностью детерминирована и выполняется в защищённом
контуре без внешних вызовов. Исходные ПД никогда не покидают сервис и не попадают
в логи/метрики.

---

## 2. Технологический стек

- **Java 21**, **Spring Boot 4.1.1**, Maven.
- **Spring MVC + виртуальные потоки** (`spring.threads.virtual.enabled=true`).
  Обработка CPU-bound (regex), блокирующих I/O нет — реактивность не нужна.
- **Spring Security** — идентификация систем-потребителей.
- **Micrometer + Spring Boot Actuator + Prometheus** — метрики.
- **Docker (multi-stage) + docker-compose** — деплой.

---

## 3. Контракт API

### `POST /process`

```
Content-Type: application/json
{ "payload": "<строка>", "payload_id": "<идентификатор>" }
  → 200
{ "result": "<строка>" }
```

Логика (один эндпоинт обрабатывает оба направления):

- **Первый запрос с новым `payload_id`** — маскирование. `payload` = исходная
  строка. Сервис возвращает маску и запоминает соответствие по `payload_id`.
- **Второй запрос с тем же `payload_id`** — демаскирование. `payload` = ранее
  возвращённая маска. Сервис возвращает исходную строку.
- Ответ всегда: `{"result": "<строка>"}`.

Направление определяется наличием `payload_id` в сторе:
- id отсутствует → маскирование;
- id присутствует → демаскирование.

### Идентификация системы-потребителя

- Через HTTP-заголовок (`X-System-Id` / API-key), проверяется Spring Security.
- Заголовок мапится на профиль системы из конфигурации.
- **Обязательный `default`-профиль** применяется, если заголовок отсутствует
  (проверяющая система шлёт запросы без заголовка) — с полным набором типов ПД
  и включённым демаскированием.

### Коды ответов

| Код | Условие |
|-----|---------|
| 200 | Успешная обработка |
| 429 | Перегрузка. Возвращается с заголовком `Retry-After`. Идемпотентно к ретраям |
| 4XX | Ошибка запроса (валидация) |
| 5XX | Внутренняя ошибка |

## 4. Архитектура

### 4.1. Слои

```
Controller (/process)
      │
      ▼
ProcessService ──► SystemConfigResolver (профиль по заголовку)
      │
      ├─► Masker ──► DetectorOrchestrator ──► [PiiDetector...]
      │                     │
      │                     └─► SpanConflictResolver
      │
      ├─► MaskingStrategy (per-type / per-system)
      │
      └─► CorrelationStore (spans by payload_id)
```

### 4.2. Детекторы ПД

Интерфейс:

```java
interface PiiDetector {
    List<Span> detect(String text);
    PiiType type();
    int priority();
}
```

- Каждый тип ПД — отдельный `@Component`. Spring собирает все в `List<PiiDetector>`.
- Новый тип ПД = новый класс, ядро не меняется.
- Оркестратор фильтрует детекторы по набору типов, разрешённых для системы.
- Идентификация не зависит от регистра.

**Обязательные типы ПД** (раздел 4.1 ТЗ):

ФИО · Дата рождения · Место рождения · Серия и номер паспорта · Гражданство ·
Орган, выдавший паспорт · Код подразделения · Дата выдачи паспорта · Серия и
номер в/у · Адрес (страна, индекс, город, улица, дом, квартира) · Email ·
Номер телефона · ИНН · Номер платёжной карты · CVV · Пин-код · Имя держателя карты.

**Различение реальных ПД от «неперсональных»**: упоминание известного лица
(поэт Пушкин), адрес отделения банка — не ПД. Реализуется словарями исключений
и контекстными проверками в детекторах.

### 4.3. Span (спан)

Непрерывный фрагмент текста с координатами:

```java
record Span(int start, int end, PiiType type,
            String original, String masked) {}
```

Используется:
- как единица метрики (span-based расстояние Левенштейна на проверке);
- как единица хранения для демаскирования.

### 4.4. Разрешение пересечений

При пересечении спанов от разных детекторов:
1. Приоритет по типу ПД (`priority()`).
2. При равном приоритете — «самый длинный/специфичный выигрывает».
3. Проигравшие спаны отбрасываются.

Детерминированно и предсказуемо.

### 4.5. Маскирование

- Стиль по примерам ТЗ: частичное маскирование с сохранением структуры
  (`Иванов Иван Иванович` → `И. И. И.`, `4509 123456` → `45** ****56`).
- За абстракцией `MaskingStrategy` — задел под токенизацию/синтетику и разный
  вид маски по системе (доп. плюсы ТЗ).
- Учитываются вариации написания: регистр; порядок дд/мм/гггг; дата текстом;
  разделяющие слова («серия хххх номер хххххх»).

### 4.6. Хранение и демаскирование

- Хранятся **спаны** (позиции + оригинальные фрагменты) по `payload_id`, а не
  весь оригинал — экономия памяти на текстах до 100k токенов.
- `CorrelationStore` — интерфейс. Реализация по умолчанию: in-memory
  (`ConcurrentHashMap` / Caffeine с TTL и ограничением размера). Подменяема на
  Redis/stateless без изменения бизнес-логики.
- Демаскирование: по сохранённым спанам оригинальные фрагменты вставляются
  обратно в присланную маску.
- **Ограничение**: случай «второй запрос с изменённым текстом под тем же
  `payload_id`» осознанно не обрабатывается (противоречит контракту, где
  `payload_id` уникален для пары маскирование→демаскирование).

## 5. Надёжность

- Глобальный `@RestControllerAdvice` — единый формат ошибок.
- **Идемпотентность** по `payload_id`: повторный запрос возвращает тот же
  результат из стора (безопасно к ретраям).
- **Бекпрешер**: при перегрузке (ограничение параллелизма/очереди) → `429` +
  `Retry-After`.
- **Graceful degradation**: ошибка отдельного детектора логируется и пропускает
  только свой тип, не роняя весь запрос.

---

## 6. Наблюдаемость и безопасность логов

- Micrometer + Actuator, экспорт `/actuator/prometheus`.
- Метрики: Latency (гистограмма), RPS, TPS (tokens per second), счётчики
  найденных ПД по типам.
- **Логи — только метаданные**: `payload_id`, список типов ПД и их количество,
  позиции/длины, latency. Сами значения ПД никогда не логируются.
- На уровне DEBUG допустимо логировать замаскированный текст (безопасно).

## 7. Конфигурация

YAML + `@ConfigurationProperties`. Пример структуры:

```yaml
pii:
  systems:
    default:
      enabled: true
      demasking: true
      types: [FULL_NAME, PASSPORT, CARD, EMAIL, PHONE, INN, ...]
    system-a:
      enabled: true
      demasking: false
      types: [EMAIL, PHONE]
```

Настраивается:
- список систем (вкл/выкл доступа);
- перечень типов ПД для идентификации/маскирования по системе;
- наличие демаскирования по системе.

Новые типы ПД добавляются классом-детектором + включением в конфиге.

## 8. Деплой

- Multi-stage `Dockerfile`: сборка через Maven → slim runtime на JRE 21.
- `docker-compose.yml` для локального запуска и прогонки.
- Поддержка http и https (self-signed допускается — проверка идёт с
  `ssl_verify=false`).
- В zip для автопроверки кода упаковываются только исходники (без
  `target/`, `.git`, зависимостей).

---

## 9. Тестирование

- **Unit** на каждый детектор: вариации форматов, регистр, ложные срабатывания
  (Пушкин, адрес банка), чек-суммы.
- **Unit** на маскирование, разрешение пересечений спанов.
- **Интеграционный** тест цикла mask→unmask по `payload_id` через MockMvc.
- Опционально: набор «золотых» примеров из ТЗ для контроля метрики 95%.

---

## 10. Границы (out of scope для базовой версии)

Реализуется архитектурный задел, но не сами фичи (раздел 6 ТЗ):
- токенизация/детокенизация и замена синтетическими данными;
- разный вид маскирования по системе;
- идентификация документов, кроме паспорта РФ;
- маскирование только при комбинации нескольких типов ПД (пин + карта).

Целевой RPS 2000 достигается естественно за счёт CPU-bound обработки и
виртуальных потоков; отдельная реализация не требуется.
