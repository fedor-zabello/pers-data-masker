# Спецификация — Модуль безопасности персональных данных

Сервис-прокси между системой-потребителем и LLM: идентифицирует персональные
данные (ПД) в тексте, маскирует их перед отправкой в LLM и демаскирует ответ.
Реализует единый контракт `POST /process` для нагрузочного тестирования.

Документ фиксирует архитектурные решения, принятые в ходе проектирования, и
служит основой для реализации. План работ — см. [PLAN.md](./PLAN.md).

---

## 1. Цели и ограничения

| Параметр | Значение |
|----------|----------|
| Качество идентификации/маскирования/демаскирования | ≥ 95% |
| Latency | ≤ 1 с (ориентир) |
| RPS | 1000 (цель), до 2000 (доп. плюс) |
| Объём текста | до 100 000 токенов |
| Таймаут одного запроса | 10 с (проверяющая система) |
| Идемпотентность | по `payload_id` (до 3 попыток) |

Ключевой принцип: обработка полностью детерминирована и выполняется в защищённом
контуре без внешних вызовов. Исходные ПД никогда не покидают сервис и не попадают
в логи/метрики.

---

## 2. Технологический стек

- **Java 21**, **Spring Boot 4.1.1**, Maven.
- **Spring MVC + виртуальные потоки** (`spring.threads.virtual.enabled=true`).
  Обработка CPU-bound (regex), блокирующих I/O нет — реактивность не нужна.
- **Spring Security** — идентификация систем-потребителей.
- **Micrometer + Spring Boot Actuator + Prometheus** — метрики.
- **Docker (multi-stage) + docker-compose** — деплой.

## 3. Контракт API

### `POST /process`

```
Content-Type: application/json
{ "payload": "<строка>", "payload_id": "<идентификатор>" }
  → 200
{ "result": "<строка>" }
```

Логика (один эндпоинт обрабатывает оба направления):

- **Первый запрос с новым `payload_id`** — маскирование. `payload` = исходная
  строка. Сервис возвращает маску и запоминает соответствие по `payload_id`.
- **Второй запрос с тем же `payload_id`** — демаскирование. `payload` = ранее
  возвращённая маска. Сервис возвращает исходную строку.
- Ответ всегда: `{"result": "<строка>"}`.

Направление определяется наличием `payload_id` в сторе:
- id отсутствует → маскирование;
- id присутствует → демаскирование.

### Идентификация системы-потребителя

- Через HTTP-заголовок (`X-System-Id` / API-key), проверяется Spring Security.
- Заголовок мапится на профиль системы из конфигурации.
- **Обязательный `default`-профиль** применяется, если заголовок отсутствует
  (проверяющая система шлёт запросы без заголовка) — с полным набором типов ПД
  и включённым демаскированием.

### Коды ответов

| Код | Условие |
|-----|---------|
| 200 | Успешная обработка |
| 429 | Перегрузка. Возвращается с заголовком `Retry-After`. Идемпотентно к ретраям |
| 4XX | Ошибка запроса (валидация) |
| 5XX | Внутренняя ошибка |

## 4. Архитектура

### 4.1. Слои

```
Controller (/process)
      │
      ▼
ProcessService ──► SystemConfigResolver (профиль по заголовку)
      │
      ├─► Masker ──► DetectorOrchestrator ──► [PiiDetector...]
      │                     │
      │                     └─► SpanConflictResolver
      │
      ├─► MaskingStrategy (per-type / per-system)
      │
      └─► CorrelationStore (spans by payload_id)
```

### 4.2. Детекторы ПД

Интерфейс:

```java
interface PiiDetector {
    List<Span> detect(String text);
    PiiType type();
    int priority();
}
```

- Каждый тип ПД — отдельный `@Component`. Spring собирает все в `List<PiiDetector>`.
- Новый тип ПД = новый класс, ядро не меняется.
- Оркестратор фильтрует детекторы по набору типов, разрешённых для системы.
- Идентификация не зависит от регистра.

**Обязательные типы ПД** (раздел 4.1 ТЗ):

ФИО · Дата рождения · Место рождения · Серия и номер паспорта · Гражданство ·
Орган, выдавший паспорт · Код подразделения · Дата выдачи паспорта · Серия и
номер в/у · Адрес (страна, индекс, город, улица, дом, квартира) · Email ·
Номер телефона · ИНН · Номер платёжной карты · CVV · Пин-код · Имя держателя карты.

**Различение реальных ПД от «неперсональных»**: упоминание известного лица
(поэт Пушкин), адрес отделения банка — не ПД. Реализуется словарями исключений
и контекстными проверками в детекторах.

### 4.3. Span (спан)

Непрерывный фрагмент текста, найденный детектором в **исходном** тексте:

```java
record Span(int start, int end, PiiType type, String original) {}
```

`start`/`end` — координаты в исходном тексте. Используется детекторами,
`SpanConflictResolver`-ом и как единица метрики (span-based расстояние
Левенштейна на проверке).

**Важно**: маскированный фрагмент почти всегда имеет **другую длину**, чем
оригинал (`Иванов Иван Иванович` — 21 символ → `И. И. И.` — 8 символов).
Поэтому координаты `Span` в исходном тексте **непригодны** для вставки
обратно в маску при демаскировании — после маскирования всех спанов позиции
в итоговой строке смещены и не совпадают с `start`/`end` из `Span`.

Для хранения соответствия «маска → оригинал» используется отдельная сущность:

```java
record MaskFragment(int maskStart, int maskEnd, PiiType type, String original) {}
```

`maskStart`/`maskEnd` — координаты фрагмента **в замаскированной строке**
(том самом результате, который сервис отдаёт клиенту и который клиент
пришлёт обратно на шаге демаскирования). Именно `MaskFragment`, а не
`Span`, сохраняется в `CorrelationStore` и используется `Demasker`-ом.

### 4.4. Разрешение пересечений

При пересечении спанов от разных детекторов:
1. Приоритет по типу ПД (`priority()`).
2. При равном приоритете — «самый длинный/специфичный выигрывает».
3. Проигравшие спаны отбрасываются.

Детерминированно и предсказуемо.

### 4.5. Маскирование

- Стиль по примерам ТЗ: частичное маскирование с сохранением структуры.
  Примеры: `Иванов Иван Иванович` → `И. И. И.`, `4509 123456` → `45** ****56`,
  `ivan@mail.ru` → `i***@mail.ru`, `+7 (900) 123-45-67` → `+7 (9**) ***-**-**`,
  `1234 5678 9012 3456` → `1234 **** **** 3456`, `123456789012` → `1234******12`.
- За абстракцией `MaskingStrategy` — задел под токенизацию/синтетику и разный
  вид маски по системе (доп. плюсы ТЗ).
- Учитываются вариации написания: регистр; порядок дд/мм/гггг; дата текстом;
  разделяющие слова («серия хххх номер хххххх»).
- **Порядок построения маски**: спаны сортируются по `start` **по убыванию**
  и применяются справа налево — так уже обработанные (более правые) позиции
  не сдвигаются при замене текущего спана переменной длины. Одновременно с
  заменой вычисляются координаты фрагмента в итоговой строке (`maskStart`/
  `maskEnd`) и формируется `MaskFragment` для каждого спана.

### 4.6. Хранение и демаскирование

- Хранятся **`MaskFragment`** (позиции в маске + оригинальные фрагменты) по
  `payload_id`, а не весь оригинал и не `Span` — экономия памяти на текстах
  до 100k токенов, и именно координаты в маске нужны для демаскирования.
- `CorrelationStore` — интерфейс. Реализация по умолчанию: in-memory
  (`ConcurrentHashMap` / Caffeine с TTL 10 минут и ограничением размера).
  Подменяема на Redis/stateless без изменения бизнес-логики.
- Демаскирование: `MaskFragment`-ы сортируются по `maskStart` по возрастанию;
  результат собирается слева направо — фрагмент текста маски до `maskStart`
  копируется как есть, далее вставляется `original`, далее пропускается до
  `maskEnd`, и так по всем фрагментам до конца строки.
- Если фрагментов для `payload_id` нет (ПД не найдены) — присланный `payload`
  возвращается как есть.
- **Ограничение**: случай «второй запрос с изменённым текстом под тем же
  `payload_id`» осознанно не обрабатывается (противоречит контракту, где
  `payload_id` уникален для пары маскирование→демаскирование).

### 4.7. Настраиваемые типы ПД через YAML

Новые типы ПД добавляются **без Java-кода** — только записью в `application.yaml`.
Кастомный тип задаётся regex-паттерном для идентификации, гибким правилом
маскирования и приоритетом. Демаскирование работает через общий
`CorrelationStore` (маска→оригинал по `payload_id`), как и для встроенных типов.

**Модель конфигурации:**

```yaml
pii:
  custom-types:
    - name: SNILS
      pattern: '\b\d{3}-\d{3}-\d{3} \d{2}\b'
      priority: 50
      masking:
        keep-start: 3        # оставить N символов в начале
        keep-end: 2          # оставить N символов в конце
        mask-char: '*'       # чем заменить середину
        preserve-separators: true   # сохранять разделители (-, пробел)
```

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| `name` | string | да | Имя типа ПД (метрики, логи, ссылки из профилей систем) |
| `pattern` | string | да | Regex для идентификации (Java `Pattern`, регистронезависимый) |
| `priority` | int | нет (0) | Приоритет при пересечении спанов (больше = важнее) |
| `masking.keep-start` | int | нет (0) | Сколько символов оставить в начале |
| `masking.keep-end` | int | нет (0) | Сколько символов оставить в конце |
| `masking.mask-char` | string | нет (`*`) | Символ маскирования |
| `masking.preserve-separators` | bool | нет (false) | Сохранять не-буквенно-цифровые символы |

**Компоненты:**

- `CustomPiiTypeProperties` — `@ConfigurationProperties(prefix = "pii.custom-types")`.
- `CustomPiiTypeRegistry` — валидация (компиляция regex, уникальность имён,
  fail-fast при старте) и доступ по имени.
- `RegexPiiDetector` — общий regex-движок; `CustomPiiDetector` оборачивает его
  и реализует `PiiDetector` (тип + приоритет из YAML).
- `FlexibleMaskingStrategy` — общий движок маскирования; `CustomMaskingStrategy`
  оборачивает его и реализует `MaskingStrategy`.
- `PiiTypeResolver` — единая точка резолва «имя типа → детектор + стратегия»:
  встроенные (enum `PiiType`) и кастомные (из реестра).

**Интеграция с профилями систем:** кастомные типы подключаются к системам по
имени в `pii.systems.<system>.types` — так же, как встроенные. `PiiTypeResolver`
резолвит имя → детектор/стратегию. При старте проверяется, что каждый `name`
в `systems.*.types` существует (встроенный ИЛИ кастомный), иначе fail-fast.

**Правило маскирования** (`FlexibleMaskingStrategy`): для фрагмента длиной `L`
оставить первые `keep-start` и последние `keep-end` символов, середину заменить
на `mask-char`; при `preserve-separators=true` не-буквенно-цифровые символы
середины сохраняются. Пример: `123-456-789 01` → `123-***-*** **`.

**Границы:** сложные контекстные проверки (словари исключений) остаются в
Java-детекторах; динамическое добавление типов в рантайме (без рестарта) — вне
базовой версии.

## 5. Надёжность

- Глобальный `@RestControllerAdvice` — единый формат ошибок.
- **Идемпотентность** по `payload_id`: повторный запрос возвращает тот же
  результат из стора (безопасно к ретраям).
- **Бекпрешер**: при перегрузке (ограничение параллелизма/очереди) → `429` +
  `Retry-After`.
- **Graceful degradation**: ошибка отдельного детектора логируется и пропускает
  только свой тип, не роняя весь запрос.

---

## 6. Наблюдаемость и безопасность логов

- Micrometer + Actuator, экспорт `/actuator/prometheus`.
- Метрики: Latency (гистограмма), RPS, TPS (tokens per second), счётчики
  найденных ПД по типам.
- **Логи — только метаданные**: `payload_id`, список типов ПД и их количество,
  позиции/длины, latency. Сами значения ПД никогда не логируются.
- На уровне DEBUG допустимо логировать замаскированный текст (безопасно).

## 7. Конфигурация

YAML + `@ConfigurationProperties`. Пример структуры:

```yaml
pii:
  custom-types:
    - name: SNILS
      pattern: '\b\d{3}-\d{3}-\d{3} \d{2}\b'
      priority: 50
      masking: { keep-start: 3, keep-end: 2, preserve-separators: true }
  systems:
    default:
      enabled: true
      demasking: true
      types: [FULL_NAME, PASSPORT, CARD, EMAIL, PHONE, INN, SNILS]
    system-a:
      enabled: true
      demasking: false
      types: [EMAIL, PHONE]
```

Настраивается:
- список систем (вкл/выкл доступа);
- перечень типов ПД для идентификации/маскирования по системе (встроенные
  и кастомные — по имени);
- наличие демаскирования по системе;
- кастомные типы ПД (`pii.custom-types`) — см. §4.7.

Новые типы ПД добавляются либо классом-детектором (встроенные), либо записью
в `pii.custom-types` (кастомные, без Java-кода) + включением в конфиге системы.

## 9. Тестирование

- **Unit** на каждый детектор: вариации форматов, регистр, ложные срабатывания
  (Пушкин, адрес банка), чек-суммы.
- **Unit** на маскирование, разрешение пересечений спанов.
- **Интеграционный** тест цикла mask→unmask по `payload_id` через MockMvc.
- Опционально: набор «золотых» примеров из ТЗ для контроля метрики 95%.

---

## 10. Границы (out of scope для базовой версии)

Реализуется архитектурный задел, но не сами фичи (раздел 6 ТЗ):
- токенизация/детокенизация и замена синтетическими данными;
- разный вид маскирования по системе;
- идентификация документов, кроме паспорта РФ;
- маскирование только при комбинации нескольких типов ПД (пин + карта).

Целевой RPS 2000 достигается естественно за счёт CPU-bound обработки и
виртуальных потоков; отдельная реализация не требуется.
